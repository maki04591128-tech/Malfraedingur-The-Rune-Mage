# INC-1 検証仕様 — spell_lab と「面白さ判定」

| 項目 | 内容 |
|------|------|
| 役割 | 本作最大リスク（コアが面白いか）を**戦闘実装前に**判定するための検証ツールと合否基準 |
| 対象 | INC-1（旧M1）。`02` の最重要ゲート |
| ステータス | Draft v0.1 |

## 更新履歴
- v0.1 初版

---

## 0. なぜこの文書が要るか

`02`（アジャイル計画）の鉄則は「コアが面白いと確認できるまで先に進まない」。だが「面白い」は曖昧語なので、**観測可能な基準**と**それを観測できるツール（spell_lab）の仕様**を先に固定する。これが無いと「なんとなく良さそう」で先に進み、後で破綻する。

検証する仮説（`02` INC-1）:

> **H: 「文法（格）を直すと呪文の手応えが目に見えて良くなる」のは、繰り返したくなるほど面白い。**

H が偽なら、`02` §4 の方向転換（文法スコープ縮小／コア再設計）をここで即決する。**戦闘・コンテンツには進まない。**

---

## 1. 2種類の検証を分ける（重要）

| | 自動テスト（正しさ） | 手動検証（面白さ） |
|---|---|---|
| 何を見る | 数式が仕様通りか | 触って繰り返したくなるか |
| 方法 | `03` §5.5 の不変条件 T1〜T5 を GUT 等で緑に | 開発者自身が spell_lab を遊ぶ＋可能なら他者 |
| 合否 | 機械的（緑/赤） | §4 の体験基準＋kill 基準 |
| 失敗時 | バグ修正 | スコープ縮小／再設計（`02` §4） |

**正しさが緑でも面白くなければ H は偽。** spell_lab は後者（面白さ）を判定するための道具。

---

## 2. spell_lab が表示すべきもの（UI 仕様）

`debug/spell_lab.tscn`（`04` §5）。戦闘なし。1画面で以下を出す。

### 2.1 入力
- 語タイル列ビルダー（`Lexicon` の全語を選べる。INC-1 はコア語彙＝効果語＋対象語＋四大元素）。
- 対象語タイルの**格サブ選択**（主格/対格…）。
- 生テキスト入力欄（無辞書モード相当の経路も同画面で試せる）。
- `C`（理解度）を**スライダで任意設定**（0–100）。実データ蓄積を待たず任意の理解度で挙動を見るため。
- ruleset 切替（入門/初級…相当の可用性。INC-1 は格一致 ON 固定でよい）。

### 2.2 単発結果パネル（1回詠唱）
`SpellEngine.cast()` の `CastResult` を**全部見える化**:
- `GrammarReport`: 規則ごと pass/fail ＋ 理由 ＋ **推奨修正**（例:「対格ではありません: `fjandi` → `fjanda`?」）。
- `P_base`（成功時威力天井）、`C`、`G`、`Control`。
- `p_misfire`（= clamp(0.10 − 0.001·C, 0, 0.10) の実値）。
- `C` がどの**重篤度バンド**か（≤30 発動失敗／31–60 実行失敗／61–99 制御失敗／100 なし）。
- 今回の解決結果（成功/暴発、暴発ならカテゴリと再解釈後の効果）。

### 2.3 バッチ結果パネル（N 回シミュレート）★最重要
暴発・ぶれは確率事象。**単発では手応えを判定できない**。「同じ呪文を N=200 回」ボタンで:
- 暴発率（実測 vs 理論 `p_misfire`）。
- 暴発カテゴリの内訳（不発/対象ズレ/自爆…のヒストグラム）。
- `effect_power` の分布（平均が `P_base` 付近に出るか＝T1 の体感確認）。
- 「格を直す前 / 直した後」を**横並び比較**で同時表示（H の核心：差が一目で分かるか）。

### 2.4 チューニングパネル（ライブ編集）
`05` BalanceConfig をその場で編集して即反映:
- `misfire.base_at_zero` / `decay_per_comprehension`
- `variance.v_max_by_tier` / `j_max_by_tier`
- `control.w_comprehension` / `w_grammar`、`word_order_bonus`
- `misfire.params`（power_drop_range / self_damage_ratio）

→ 「**どう調整しても面白くならない**」のか「**チューニングで面白くなる**」のかを判定するため。kill 判断の前に必ずチューニングを試す。

## 3. 必須テストシナリオ（毎セッション走らせる固定セット）

開発者は毎回これらを spell_lab で再現し、§4 の基準で評価する。

| ID | 入力 | C | 期待される観測（質的） |
|----|------|---|------------------------|
| S1 | `meiða fjanda`（対格・正） vs `meiða fjandi`（主格・誤） | 50 | 正は狙い通り命中、誤は弱く外れ、`GrammarReport` が `fjandi→fjanda` を提示。**差が即分かる** |
| S2 | S1 を C=0 / 50 / 100 で | 各 | C 上昇で暴発率が 10%→5%→0% に低下。暴発の質が不発→実行失敗→自爆へ重篤化 |
| S3 | 強ティア未習語を含む正しい呪文 | 0 | 成功すれば高威力だが約10%暴発・暴発時は不発（軽傷）。「博打感」が成立するか |
| S4 | 文法正・C 高 | 90 | ほぼ決定的。稀な暴発は自爆。達人の緊張感が出るか |
| S5 | 無辞書経路で語形を綴り誤り | 50 | タイル経路と同じ判定に正規化されるか（`03` §4） |
| S6 | 語順崩し（正準形から外す） | 50 | 語順ボーナス消失が威力に出る。崩しすぎの体感 |

シナリオは `tests/scenarios/*.json` 等で固定化し、ワンクリック再現できること（再現性＝seed 固定、`03` §8）。

## 4. 面白さの合否基準（H の判定）

§3 を触った上で、開発者（可能なら他者2〜3名）が以下を評価する。**数値ではなく体験**を見る。

### 4.1 通過条件（すべて満たす）
1. **発見可能性**: 説明なしで S1 を触り、「誤を正に直すと良くなる」と**5分以内に自力で気づく**。
2. **手応えの可視性**: 格を直した瞬間、結果の改善が**1〜2回の試行で体感できる**（バッチ比較で差が明白）。
3. **是正の有用性**: `GrammarReport` の推奨修正が「次どうすればいいか」を**実際に教えている**（迷子にならない）。
4. **戦略的緊張**: S3/S4 で「強い未習語を博打で撃つ／安全な既習語で堅実に」の**選択に迷いが生じる**。
5. **反復意欲**: 「もう一回最適化したい」と**自然に手が伸びる**（指示なしで複数回試す）。

### 4.2 計測（主観を記録する）
- 「最初の正しい呪文」までの時間（目標 < 5分、`01` 8章と整合）。
- 各観点を 5 段階自己申告（1=退屈 5=やめられない）。中央値で見る。
- 他者テスト時、声に出して操作してもらい「なぜそうした」を記録（思考の可視化）。

### 4.3 kill 基準（H が偽の判定）
次のいずれかが、**チューニングパネルで調整を尽くしても**該当する場合、H は偽:
- 通過条件 1〜2 が満たせない（差が分からない/気づけない）。
- 4.2 の中央値が 2 以下が支配的。
- 「直す作業が面倒なだけで楽しくない」という反応が多数。

→ `02` §4 の方向転換を即決：(a) 文法スコープを縮小（格一致以外を削る）して再検証、(b) それでも偽ならコアメカニクス再設計。**この時点で曲げるのが本ゲートの目的**。コンテンツ・戦闘には進まない。

---

## 5. 進行判断（このゲートの出口）

| 結果 | 次アクション |
|------|--------------|
| 自動テスト緑 ＋ §4.1 全通過 | INC-2（戦闘の手応え）へ進む |
| 自動テスト緑 ＋ §4.1 一部不通過 | チューニング→再評価。原因を §3 のどのシナリオで割れるか特定 |
| §4.3 kill 基準該当 | スコープ縮小 or 再設計（`02` §4）。**前進し続ける**（失敗ではなく早期発見） |
| 自動テスト赤 | バグ修正（面白さ判定はその後） |

> 本ゲートは「面白くなければ早く知る」ための装置。kill 判定はプロジェクトの失敗ではなく、アジャイルの設計された前進（`02` §0/§4）。
